# Task-Audit：任務書完成度誠實稽核

> 核心原則：**status:done 但勾選框全空 = 沒有稽核。**
> 驗收標準是唯一完成依據——沒做到的不打勾，打了勾的必須有證據。

## 輸入

| 項目 | 預設路徑 |
|---|---|
| 任務書 | `~/tasks/<專案>/tasks/T*.md` |
| 程式碼 | `~/Projects/<專案>/` |
| 演算法規格（若有） | `~/tasks/<專案>/algs/*.md` |

## 流程

### 步驟 1：結構驗證

執行 `~/.pi/agent/skills/spec-to-tasks/scripts/validate_tasks.py <專案名>`，
先修完所有結構問題（frontmatter 缺欄/格式/依賴引用）再進入深度稽核。

### 步驟 2：逐張稽核 status:done 的任務書

對每一條驗收標準，對照**實際程式碼與測試**判定三態：

| 判定 | 條件 | 處理 |
|---|---|---|
| ✅ 已達成 | 有實作＋有測試佐證（或有明確可驗證產出） | `- [ ]` → `- [x]` |
| ⬜ 未達成 | 未實作／實作了但無驗證／只有模糊引用 | 保持 `[ ]`，列入未竟事項 |
| 🔀 部分達成 | 主體完成但有具名小項缺失 | 主體打勾，缺項另立新 checkbox 保持未勾 |

**禁止事項**：
- 不得因「大概做了」就打勾——打勾必須能指出測試名稱/程式碼位置/產出檔案
- 不得為了讓 status:done 成立而放水打勾
- 引用演算法檔的條目，須核對該檔小節內容確實被實作（不是只引用了檔名）

### 步驟 2.5：接線審計（元件層稽核後必做）

> 源自 ai-oncall 稽核教訓：19 張任務書個個有測試佐證，但 daemon 收到警報後
> 根本不會觸發分診——「零件都有、沒人接線」的缺口無法靠逐條找證據抓到。
> 元件層稽核通過後，另執行以下三項機械化檢查：

#### A. Env var 消費者審計

每個環境變數列出 **production code** 的讀取處；只有測試讀取的標記 ⚠️。

```bash
# 例：找出定義了但無人讀取的 env var
grep -rn "os.environ\|os.getenv" <src>/ --include="*.py" | grep -v test
grep -rn "os.LookupEnv\|os.Getenv" <gate>/ --include="*.go" | grep -v _test
```

#### B. Public 函式 caller 審計

「有實作＋有測試＋**無 production caller**」＝接線缺口候選：

```bash
for sym in NewSender FanOut provider_chain_from_env; do
  echo "-- $sym"
  grep -rln "$sym" cmd/ src/ --include="*.go" --include="*.py" \
    | grep -v test   # 只剩定義處/測試 = 缺口
 done
```

#### C. 主流程圖逐箭頭比對

把 spec 主流程 mermaid 圖的**每個箭頭**列出，逐一指出「在哪段 code 發生」，
而非只比對功能方塊是否存在。斷在半空的箭頭即為接線缺口：

| 流程箭頭 | code 位置 | 狀態 |
|---|---|---|
| 警報 → 分診觸發 | grpc_servicer.py:ReportIncident | ✅ |
| 報告 → Telegram 推播 | ??? | ❌ 缺口 |

#### D. 入口級煙霧測試規則

每個系統至少一個測試從**真實入口**（daemon 啟動→網路埠→請求）走到可觀察副作用，
且斷言下游效應（如「LLM 端點收到請求」「predictions 入库」），
不得只從內部呼叫被測物件——作者寫的元件級測試會帶著與實作相同的盲點。

### 步驟 3：缺口處理

對發現的未達成項，依成本分流：

1. **可快速補（<15 分鐘）**：直接補實作＋補測試，獨立 commit
   （訊息格式：`fix(<scope>): 補齊 T0XX 稽核發現的缺口`），然後才打勾
2. **中等工作量**：列為該任務書的「執行紀錄 → 未竟事項」，保持已打勾的主體，
   缺項保持未勾
3. **重大缺口（多項核心未達成）**：任務書 status 降回 **in-progress**，
   列明剩餘工作——**不得維持 done**
4. **整合缺口回流為新任務書**：接線審計（步驟 2.5）發現的跨任務缺口
   （如「元件有實作但無 production caller」「流程箭頭斷在半空」）
   屬於沒有 owner 的工作，僅列未竟事項不會被追蹤執行——必須：
   - 建立新任務書（編號接續現有最大值），frontmatter `depends_on` 填入
     被引用的元件任務（須皆為 done），驗收標準必須含**入口級 e2e 斷言**
     （見步驟 2.5-D），並在內文註明「來源：T0XX 稽核接線審計」
   - 在原發現缺口的任務書執行紀錄加註：「已回流為 T0XX」
   - 操作者手動工具（如離線評測 CLI）定位上可接受不入 daemon 接線，
     但須在新任務書或執行紀錄中明示此決策

### 步驟 4：執行紀錄

每張稽核過的任務書附加：

```markdown
## 執行紀錄（YYYY-MM-DD 稽核）
- 已達成 N 項並打勾。
- **未竟事項**：<具體列出未勾選項與原因>
- 補充：<實作差異聲明（如驅動替換、方案調整）>
```

### 步驟 5：彙總報告

向使用者報告：

```
== 最終勾選統計 ==
T001 ✅2 ⬜1 …（逐張）
合計：✅N ⬜M

== 未竟項分類 ==
- 條件式任務：N 項（等外部條件）
- 整合缺口：N 項（列清單）
- 小項：N 項

== 本輪修復 ==
- 補實作清單（含 commit）
```

## 實戰教訓（源自 slo-sentinel 首輪稽核）

| 教訓 | 案例 |
|---|---|
| daemon 沒接熱載入 | T009 驗收寫了「rules.d 熱載入→下一輪詢生效」，但 daemon 從未呼叫 catalog.Watch——稽核後補線 |
| UI 只做了一頁 | T016 五張頁面只做一張 → 稽核後降級 in-progress |
| 測試期望本身算錯 | §A.7 案例 U=30% 但 ETA_agg<6h 應為 critical，原測試期望 warning——稽核時以規格公式重算修正 |
| 驗收細節外包給引用 | 「依 §X 全數實作」導致執行者略過——稽核時須展開逐條比對 |
| **零件都有、沒人接線**（ai-oncall） | 19 張任務書個個有測試，但 daemon 收到警報不會觸發分診；env var 範本有 OPENAI_API_KEY 但無人讀取——步驟 2.5 接線審計即為此而設 |
| **e2e 繞過入口**（ai-oncall） | 作者寫的 e2e 直接呼叫 TriagePipeline 而非從 gRPC 邊界進入，恰好掩蓋接線斷裂——步驟 2.5-D 入口級煙霧測試規則即為此而設 |
| **缺口只記備忘不會被執行**（ai-oncall） | 接線審計發現的四個缺口只寫在執行紀錄「已列為下一批次工作」，但無任務書即無追蹤——步驟 3-4 回流規則即為此而設 |
