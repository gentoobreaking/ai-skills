# Spec-to-Tasks：規格書 → 任務書拆分

將 `~/tasks/<專案>/` 下的規格書拆解為可執行的任務書。本 skill 固化了實戰中踩過的教訓：
**附錄式演算法會被遺失、模糊引用會被略過、外部依賴要顯式聲明**。

## 輸入約定

| 項目 | 預設路徑 | 說明 |
|---|---|---|
| 主規格書 | `~/tasks/<專案>/spec.md` or `~/tasks/<專案>/*.md` | 定位/目的/功能清單/模組樹/流程圖 |
| 演算法規格 | `~/tasks/<專案>/algs/*.md` | 各模組的詳細演算法定義（可能不存在，見步驟 2） |
| 任務範本 | `~/Projects/ai-skills/clw-ideas2tasks/templates/task-template.md` | 可由使用者指定其他路徑 |
| 輸出目錄 | `~/tasks/<專案>/tasks/T###-kebab-name.md` | |

三個路徑皆可被使用者指定覆寫——以使用者訊息中的路徑為準。

## 流程

### 步驟 1：讀取全部輸入

- `read` 範本、spec.md、所有 algs/*.md（**必須全文讀完，不可只讀開頭**）
- 若 `tasks/` 已有任務書：讀取既有編號與狀態，新任務接續編號，不覆蓋已存在檔案

### 步驟 2：規格書健檢（拆分前審查）

逐項檢查，有缺口先向使用者提出再動工：

- [ ] 有「非目標（Non-goals）」嗎？沒有 → 提醒補上，防止範圍膨脹
- [ ] 功能清單是否有編號（F1–Fxx）？拆分後的追溯矩陣需要它
- [ ] 演算法細節在哪？若只在 spec 正文附錄或根本沒有 → **建議先拆 `algs/*.md`**
  （附錄式設計會被遺失——這是實測過的教訓），並建立防遺失索引結構（見步驟 5）
- [ ] 標注「後期/選配/v2」的功能：仍要拆出條件式任務書（見步驟 4 規則 D），
  但需與使用者確認前置條件為何
- [ ] 外部依賴（其他專案/服務/API）：記錄下來，對應任務書用 `blocked_on` 聲明

### 步驟 3：設計任務地圖

1. 從模組樹＋功能清單推導任務：**每個模組至少一張；每個演算法檔至少一張；
   每個「必須實作」功能至少落在一張內**
2. 基礎設施任務（骨架/config/store/CLI）排最前，e2e 整合測試排最後
3. 畫依賴圖（文字即可）：依賴關係就是施工順序；禁止循環
4. 支援性任務（無獨立演算法但必要，如骨架、唯讀 API、部署文件）單獨列表——
   它們不對應功能編號，但缺了系統跑不起來
5. 粒度原則：**單張任務書在一個 agent session 內可完成**（經驗值 25–50 行）

### 步驟 4：產出任務書

#### frontmatter 規範（照範本欄位）

```yaml
---
github_issue: N/A
title: <中文標題，含模組路徑>
type: feat | fix | chore | docs | test
priority: high | medium | low
status: pending          # 只允許 pending/done/in-progress；新建一律 pending
depends_on:              # 任務編號列表；無依賴寫 depends_on: []（一行，勿拆列）
- T00X-xxx
assignee: "<使用者指定的 assignee>"
created: <今天日期>
updated: <今天日期>
blocked_on:              # 僅條件式任務需要；列出外部/時間前置條件
- "<條件描述>"
---
```

- 檔名：`T###-kebab-name.md`（三位數零填充）
- `created` = `updated` = 今天日期；之後狀態變更時同步 `updated`

#### 內文規範

```markdown
# T### - 標題

## 目標
（做什麼；含模組路徑；若受約束，第一行放 ⛔ 約束聲明）

## 驗收標準
- [ ] （具體、可勾選、可測試的枚舉項）

## 備註
（風險、對應規格章節、與其他任務的介面）
```

#### 驗收標準撰寫鐵律（最重要）

1. **展開而非引用**：「依 §A.5 全數實作」是壞例子——把 §A.5 的四條規則連預設值
   逐一列成 checkbox。執行者不應該需要來回翻閱才能知道要做什麼；
   演算法檔降級為深究原理時的參照
2. **固定測試案例**：演算法檔若有數值例，轉成斷言具體數字的測試要求
3. **枚舉語料集**：解析/驗證類任務要求 ≥N 個壞輸入案例，逐一斷言行為
4. **介面契約**：基礎任務（store/query/provider）要在驗收標準定義 interface 簽名，
   因為下游任務依賴它
5. **安全邊界**：涉及認證/遮蔽/執行面的任務，驗證項必須包含「負面測試」
   （未授權/畸形輸入的拒絕行為）

#### 條件式任務規則（後期/選配/外部依賴功能）

```yaml
blocked_on:
- "<具體前置條件，可驗證的描述>"
```

- 目標第一行：`> ⛔ 本任務受外部條件約束：blocked_on 全數滿足前不得開工。
  排程器挑到時應先逐項驗條件，未滿足則跳過並記錄原因。`
- priority 一律 low；功能設計仍要預先想好寫進任務書（屆時解鎖即可直接開工）

### 步驟 5：追溯索引寫回 spec.md

在 spec.md 加入（或更新）「演算法規格文件索引（任務拆解必讀）」章節：

```markdown
| 演算法檔 | 對應功能 | 對應模組 | 對應任務 |
|---|---|---|---|
| [algs/xxx.md](algs/xxx.md) | F#… | internal/xxx/ | **T0XX** … |
### 支援性任務（無獨立演算法檔但必要）
### 延後批次任務（有任務書、鎖在外部條件後）→ 指向 blocked_on 任務書
```

同時在功能清單中，後期/選配項目標注「任務書 T0XX（受外部條件約束 …）」。

### 步驟 6：驗證

以腳本或人工逐項確認：

- [ ] 所有任務書首行為 `---`（frontmatter 完整）
- [ ] `depends_on` 引用的任務編號全部存在；無循環
- [ ] `depends_on: []` 為單行格式（不是列表項 `- []`）
- [ ] status/assignee/created/updated 齊備且格式正確
- [ ] 覆蓋矩陣：功能清單每一項 F 都能對到 ≥1 張任務書（或標注延後＋任務書存在）
- [ ] 演算法檔每一份都能對到 ≥1 張任務書
- [ ] 驗收標準無「依 §X 全數實作」型態的模糊引用（必須展開）

完成後向使用者報告：任務總數、依賴圖（文字）、條件式任務清單、覆蓋矩陣位置。

## 品質備忘（拆分時常犯的錯，源自實戰）

| 教訓 | 說明 |
|---|---|
| 附錄會遺失 | 演算法細節放附錄＝執行者永遠不不讀。獨立成檔＋任務書強制引用 |
| 展開而非引用 | 「見 §X」不算驗收標準；枚舉到可勾選粒度 |
| 模組結構 ≠ 實作深度 | 外包計算不會減少模組數量，只改變模組內部實作——兩者別混為一談 |
| 站在成熟工具上 | 先查有無開源品（如 Sloth）；自研部分聚焦差異化增量 |
| 單一通知/執行路徑 | 同一事件多條觸發路徑＝雙重通知；設計時就定案唯一路徑 |
| 看得到的人 ≠ 動手的人 | 報告類工具的價值在主動推播到維護者手上，不在 console |
